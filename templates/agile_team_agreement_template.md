# アジャイル・スクラム開発 チーム合意事項テンプレート

アジャイル（スクラム）開発を始めるにあたり、**「チーム全員で合意して決めるべき具体的なルール」**のテンプレートです。
プロジェクト開始時の「準備期 (Sprint 0)」などにチームでディスカッションしながら埋めていき、完成したものをチームの共通ルール（ワーキングアグリーメント）として運用してください。

---

## 1. チームの役割とメンバー (Roles & Members)

チームの各ロールを誰が担当するか、および連絡先を明確にします。

| ロール | 担当者名 | 主な連絡先（Slack等） |
| :--- | :--- | :--- |
| **プロダクトオーナー (PO)** | ［名前を入力］ | ［@メンション名等］ |
| **スクラムマスター (SM)** | ［名前を入力］ | ［@メンション名等］ |
| **開発チーム (Developers)** | ［名前を入力］<br>［名前を入力］ | ［@メンション名等］ |

---

## 2. チームの基本ルール (Working Agreement)

円滑にコミュニケーションを取るためのルールを定義します。

* **コアタイム / 稼働時間**:
  * ［例：10:00 〜 17:00 は原則連絡が取れる状態にする］
* **コミュニケーションツール**:
  * メイン連絡先：［例：Slackの #project-xyz チャンネル］
  * ビデオ通話ツール：［例：Google Meet / Zoom］
* **リアクションとレスポンスのルール**:
  * ［例：確認したメッセージにはメンションやスタンプで必ずリアクションする］
  * ［例：緊急時は直接メンションまたは通話で連絡する］

---

## 3. スクラムイベントのスケジュール (Scrum Events Schedule)

各ミーティングの時間、頻度、URLをカレンダーに固定します。

> [!TIP]
> デイリースクラムは毎日同じ時間・同じ場所で実施するのが原則です。

| イベント名 | 実施頻度 / 曜日 | 実施時間帯 | ミーティングURL |
| :--- | :--- | :--- | :--- |
| **スプリントプランニング** | ［例：隔週月曜日］ | ［例：10:00 - 11:30］ | ［URLを入力］ |
| **デイリースクラム** | ［例：平日毎日］ | ［例：10:00 - 10:15］ | ［URLを入力］ |
| **リファインメント** | ［例：毎週水曜日］ | ［例：15:00 - 16:00］ | ［URLを入力］ |
| **スプリントレビュー** | ［例：隔週金曜日］ | ［例：15:00 - 15:45］ | ［URLを入力］ |
| **レトロスペクティブ** | ［例：隔週金曜日］ | ［例：16:00 - 17:00］ | ［URLを入力］ |

## 4. 準備完了の定義 (Definition of Ready: DoR)

プロダクトバックログのアイテムを「スプリントプランニングに持ち込んで良い（開発に着手できる）」と判断するための基準です。

> [!IMPORTANT]
> これを怠ると、スプリント中に「仕様がわからないから開発が進まない」という手戻りが発生します。

* [ ] ユーザーストーリーのフォーマット（「〜として、〜したい、なぜなら〜」）で書かれている。
* [ ] **受け入れ基準（何ができたら完成か）**が具体的に明記されている。
* [ ] デザイン（モックアップ・Figma等）や必要な仕様書が添付、またはリンクされている。
* [ ] 開発チームによるストーリーポイントの見積もりが完了している。
* [ ] スプリント内で完了可能なサイズ（目安：［例：8ポイント以下］）に分割されている。

---

## 5. 完成の定義 (Definition of Done: DoD)

タスクを「スプリント内で完了（Done）した」と見なすための共通基準です。

> [!WARNING]
> 「実装は終わりましたが、テストやデプロイはまだです」という未完成のインクリメントがスプリントレビューに持ち込まれるのを防ぎます。

* [ ] コーディング規約に沿って実装され、不要なコードが整理されている。
* [ ] 実装したコードに対するコードレビューが行われ、［例：1名以上］のApproveを得ている。
* [ ] ローカルまたはCI上でユニットテスト（自動テスト）が全件パスしている。
* [ ] 開発環境またはステージング環境へのデプロイが完了している。
* [ ] チケットに記載された「受け入れ基準」を全て満たし、動作検証が行われている。
* [ ] 関連するドキュメント（必要に応じて）の更新が完了している。

---

## 6. ツールの運用ルール (Tool Guidelines)

進捗状況を正確に可視化し、コード管理を円滑にするためのルールです。

### プロジェクト管理ツール (Jira, GitHub Projects, Trello等)
* **ツールのURL**: ［プロジェクトボードのURLを入力］
* **ステータス更新のタイミング**:
  * ［例：作業開始時に「In Progress」へ、レビュー依頼時に「In Review」へ、マージ完了時に「Done」へ更新する］
  * ［例：デイリースクラムの開始前までに、各自最新のステータスに更新しておく］

### ソースコード管理 (GitHub, GitLab等)
* **リポジトリURL**: ［リポジトリのURLを入力］
* **ブランチ戦略**: ［例：GitHub Flow（mainブランチからfeatureブランチを切り、PRでマージする）］
* **コミット/PRのルール**:
  * プルリクエストには関連するチケット（Jira等）のIDを紐付ける。
  * レビュー依頼時のメンションルール（［例：Slackの #review-request チャンネルで共有する］）。
