# 既習のウォーターフォール用語からScrumを見る

これは「同じものの名前を置き換える表」ではありません。ウォーターフォールで学んだ概念を足場に、**Scrumでは意思決定のタイミングや責任の持ち方がどう変わるか**を見るための比較表です。

| 既習の観点 | Scrumで近く見えるもの | 重要な違い |
|---|---|---|
| プロジェクト目的・要求 | Product Goal / Product Backlog | Backlogは最初に固定せず、学習に応じて創発・並べ替えされる |
| 要件一覧 | Product Backlog Item | ScrumはPBIの書式を規定しない |
| 工程計画 / WBS | Sprint Backlog | 固定工程表ではなく、Sprint中も更新される実行可能な計画 |
| マイルストーン | Sprint Goal | タスク完了数ではなく、そのSprintで達成したい価値・目的へ焦点を置く |
| 進捗会議 | Daily Scrum | 管理者への報告ではなく、DevelopersがGoalへの進捗を検査し計画を適応する |
| 成果物レビュー | Sprint Review | 検収だけでなく、stakeholderと成果・環境を検査して次を適応する |
| 品質基準 / 完了条件 | Definition of Done | Increment全体に透明な品質基準を与えるScrum公式Commitment |
| 振り返り / lessons learned | Sprint Retrospective | プロジェクト終了時だけでなく、毎Sprintで働き方を改善する |
| 変更要求管理 | Product Backlogの更新・scope再調整 | 変更を例外処理だけでなく学習として取り込む。ただし無制限な割り込みではない |

## 一番大きな差

ウォーターフォールの学習では、次のようなイメージを持ちやすいです。

```text
前工程で決める
↓
後工程でその決定に従う
↓
変更が必要なら変更管理する
```

Scrumでは、複雑な仕事について次のループを意図的に短くします。

```text
現時点で最善の計画
↓
実行して結果を得る
↓
検査して新しい知識を得る
↓
計画やBacklogを適応する
```

## 変わらないもの

Scrumでも次は必要です。

- 利用者・業務を理解する
- 設計する
- 実装する
- テストする
- セキュリティや品質を考える
- リスクを管理する
- 必要なドキュメントを残す

「工程が消える」のではなく、**価値を届けて学べる小さな単位の中へ工程を組み込む**と捉えると理解しやすくなります。

## 注意：Scrumを小さいウォーターフォールにしない

次のようにすると、2週間ごとにウォーターフォールを繰り返すだけになりやすいです。

```text
Sprint前半: 全設計担当
Sprint中盤: 実装担当
Sprint後半: テスト担当
```

必要な専門性はあっても、Scrum Teamは1つのSprint GoalとDoneなIncrementへ協働します。工程間の受け渡しを短くするだけでなく、**フィードバックを得ながら全体で適応できる状態**を目指します。
